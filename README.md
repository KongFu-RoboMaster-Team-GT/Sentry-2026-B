# Sentry-2026-B：原 FINAL-2026 + 双板通信

当前改动与原版的逐项核对、确认回归及剩余限制，见[双板改动审查](docs/dual-board-change-audit.md)。

以仓库原版FINAL-2026为基准，完成上下板分工、CAN转发和实机暴露的控制问题修正：
保留底盘PID和pitch滑模增益、目标转速、pitch角度定义、遥控解码公式和开火拨杆逻辑。针对实机反馈修正yaw角度连续性、底盘云台坐标零位及前进轴，并增加起停缓变；仅在上板yaw调试分支降低位置纠偏强度并增加反馈方向观察，原单板分支保留。

## 原工程与双板目标

- 原工程：`MDK-ARM/FINAL-2026.uvprojx`，默认 `BOARD_ROLE=0`，保留单板运行路径。
- 双板工程：`MDK-ARM/dual_board.uvprojx`，分别选择 `UPPER` 和 `LOWER` 编译、烧录。
- `Task/shooter_task.c`、`Task/ins_task.c` 保持原版；`Task/gimbal_task.c` 的上板分支修正yaw跨界、初始化及模式切换目标连续性，并使用单独的yaw调试参数。`Task/chassis_task.c` 增加下板操作快照入口、断流时清PID/停机、同步原校准清零及只读诊断；有效输入时执行原来的1ms控制循环，PID、跟随、解算、输出倍率不变。
- `remote_control.c` 和 `control_task.c` 仅在原解析成功后记录接收时间，不改写原解析结果。
- 撤回上一版新增的中立 500ms 解锁、模式 0 停机、VTM 合并/强制在线、所有电机与 IMU 就绪门槛、pitch 相对角参考，以及额外 PID 清零等改动。
- 原 `FINAL-2026.uvprojx` 的本机调试设置和用户的 FreeRTOS 文件改动保留，不随本次回退覆盖。

## 接线与执行位置

| 项目 | 上板 | 下板 |
|---|---|---|
| 接收机 | 保持原接口 USART3 | 不接收机 |
| CAN1 | 共享总线上的 pitch、摩擦轮、拨弹由上板控制，同时连接下板 CAN1 | 接收板间命令、转发 CAN2 电机反馈 |
| CAN2 | 不接本方案下板电机 | 四个底盘电机和 yaw |
| 控制算法 | 原云台、发射、IMU 任务；读取原遥控/VTM 数据 | 原底盘 PID 任务每 1ms 使用本地 CAN2 转速和 yaw 编码器，执行上板转发的 yaw 电流 |

上板与下板 CAN1 的 H/H、L/L 对接并共地。上下板 CAN2 不互连。
上板必须随云台运动，原云台任务继续使用上板自身 IMU。
CAN1 共享总线只允许上板发送电机控制帧，避免两块板互相覆盖。

| 总线 | 电机反馈 ID | 原电机控制帧 |
|---|---|---|
| CAN1 | 摩擦轮 0x201、0x202，拨弹 0x203 | 0x200 的第 1、2、3 槽 |
| CAN1 | pitch 0x206 | 0x1FE 第 2 槽 |
| 下板 CAN2 | 底盘 0x201–0x204 | 0x200 第 1–4 槽 |
| 下板 CAN2 | yaw 0x205 | 0x1FE 第 1 槽 |

拨弹 C610 ID 3 与底盘 ID 3 在不同总线上，不冲突，不用改号。

## 烧录

需要 Keil MDK 5、ARM Compiler 5、STM32F4xx DFP 2.8.0；芯片 STM32F407IGHx。

1. 打开 `MDK-ARM/dual_board.uvprojx`。
2. 选 `UPPER`，ST-Link 接上板，F7 编译、F8 下载。
3. 选 `LOWER`，ST-Link 接下板，F7 编译、F8 下载。
4. 两板重新上电。首次架空底盘、移除弹丸，逐项核对方向与通信。

也可在根目录执行 `scripts/build_dual_board.ps1`，只编译并复制，不自动烧录：
`firmware/UPPER.hex` 给上板，`firmware/LOWER.hex` 给下板。

**本版通信协议为版本 3，与版本 1/2 不兼容。上板和下板都必须重新编译、烧录，不能只换其中一块。**
不要把同一份 HEX 烧到两块板。

## 遥控与 Watch

不新增任何拨杆模式或解锁操作，遥控字节解码和拨杆功能保持原样。已根据实测将双板底盘前进速度取自 ch1 正方向、横移取自 ch0；这发生在解码后的速度坐标映射处，不改变接收机通道数据。
原代码中 `rc_ctrl.rc.ch[6]` 是有符号通道值，可以是 -1；Watch 十六进制的 `0xFFFF` 就是 short 的 -1。
原有转换函数将负通道值映射为 `key.sw=1`，非负值映射为 `key.sw=0`。
因此观察原程序的 **0/1 模式变化应添加 `key.sw`**，不能把原始 ch6 强行改成 0/1 来修复显示。

在 Keil Debug 模式下勾选 **View → Periodic Window Update**，使 Watch 在 Run 时周期刷新。
若不勾选，Stop 后才刷新是界面行为，不表示遥控接收中断停止。这个设置不通过修改固件实现。

`board_armed` 只作兼容调试指示：
上板表示近期收到了原遥控/VTM 数据，下板表示近期收到了有效且启用的底盘操作快照，
不再是需要另外解锁的状态机，也不再等待全部电机反馈或 IMU 温度。

`board_rx_count` 是有效板间数据累计数，`board_tx_fail_count` 是发送邮箱未排入的累计数。
`board_remote_motor_mask` 的 bit0–4 对应下板底盘 1–4 和 yaw 是否有近期反馈，仅用于排查，不作为全车使能门槛。

### 下板控制数据始终为 0 时

两板都上电并 Run，在各自 Keil Watch 添加 `board_diag` 并展开。
本诊断不改变协议版本、使能条件、遥控映射或控制器参数；CAN1 接收读取失败时直接丢弃，避免处理未初始化数据。

| 字段 | 含义与预期 |
|---|---|
| `role` | 上板必须为1，下板必须为2；用来核对实际运行固件角色 |
| `protocol_version` | 两板均应为3 |
| `poll_count` | 板间任务执行次数，运行时应持续增加 |
| `chassis_tx_queued_count` | 上板0x320成功排入发送邮箱的次数；不表示对端已收到 |
| `can1_rx_count` | CAN1成功从接收FIFO读取的全部报文数，尚未做协议校验 |
| `last_can1_id` | 最近成功读取的CAN1报文ID，建议十六进制观察 |
| `can1_invalid_frame_count` | 非标准8字节数据帧计数 |
| `can1_rx_error_count` | HAL读取CAN1接收FIFO失败的次数 |
| `chassis_frame_count` | 下板收到0x320标准8字节数据帧的次数，包括协议校验失败的帧 |
| `chassis_rx_version` | 下板最近收到0x320帧中的版本字段，应为3 |
| `chassis_reject_reason` | 最近0x320帧处理结果：0接受、1版本错、2校验错、3通道越界、4序号未前进；只有帧计数非零时才有意义 |
| `can1_esr` | 每次板间任务采样的CAN1 ESR原值，保留十六进制值用于后续诊断 |
| `can1_hal_error` | 每次板间任务采样的HAL累计错误码；不能单独当作当前故障判据 |

下板`can1_rx_count`始终0，需继续查上板是否发送、CAN1物理链路、控制器状态及接收中断；
若该数增长但`chassis_frame_count`为0，则CAN1在收数据，却没收到0x320控制帧。
若`chassis_frame_count`增长而有效计数`board_chassis_rx_count`不增长，根据拒收原因区分固件版本、校验、通道或序号问题。
调试时保持另一块板运行；暂停上板会让下板约100ms后停止输出，但不会把已累计的接收计数清零。

### 收到指令但下板电机不动作，或进入 Debug 后才恢复

下板新增只读诊断`lower_diag`，需要下载包含该变量的LOWER版本；上板固件、协议3、遥控映射和电机控制参数不变。
诊断字段本身只读，不解除yaw保护、不强行发送非零测试指令。运行期CAN故障恢复见下一节。
CAN2读取失败或非标准8字节数据帧直接丢弃并计数，避免拿无效反馈更新电机数据。

| 字段 | 含义 |
|---|---|
| `chassis_loop_count` | 实际底盘任务循环次数；持续增加才说明任务在执行 |
| `ch0`、`ch1`、`mode` | 底盘任务实际采用的操作快照；手动模式mode=0，摇杆回中约1024 |
| `motion_enabled`、`yaw_enabled` | 最近板间任务采样的底盘/yaw通信使能；两者独立 |
| `chassis_command[4]` | 限制通信使能后，最近请求发往CAN2的四轮指令；邮箱失败时仍保留请求值 |
| `yaw_received`、`yaw_command` | 最近收到的上板yaw指令，以及下板最终请求发送的yaw指令 |
| `can2_rx_count`、`last_can2_id` | CAN2成功读取的全部帧次数及最近ID |
| `motor_rx_count[5]` | 底盘ID1–4和yaw五路有效电机反馈累计次数 |
| `can2_tx_queued_count`、`can2_tx_fail_count` | CAN2成功排入邮箱/未排入次数；入队不代表总线发送完成或收到ACK |
| `can2_rx_error_count`、`can2_invalid_frame_count` | CAN2读取失败/帧格式无效次数 |
| `can2_state`、`can2_error` | HAL状态和累计错误码；正常已启动CAN的HAL状态为2(LISTENING) |
| `can2_mcr`、`can2_msr`、`can2_tsr`、`can2_esr` | 每毫秒板间任务采样的CAN2控制/状态/发送/错误寄存器，保留十六进制用于诊断 |

`ESR=0`不能单独证明CAN2在发送或电机已收到指令；必须结合任务、指令值、HAL状态、发送寄存器和反馈判断。
状态是在采样时取得，不能用进入Debug并复位之后的正常值，证明复位前无故障。

当前LOWER保存的Keil设置启用了Update Flash Before Debugging、Load Application at Startup及Run to main()，
因此进入Debug可能重新下载并改变复位/执行时序；Run to main()只是运行到main并暂停，不代表独立上电自动运行已经验证。
若“平时不动、进Debug再Run就恢复”，先在摇杆回中、发射关闭时对比：
不进入Debug，只按下板硬件RESET能否恢复；再检查Flash Download中的Reset and Run、正常下载的目标是否为LOWER、
以及移除调试器供电后的真实冷启动行为。还未通过这些实机检查前，不认定是CAN初始化时序、BOOT配置或下载设置中的某一项。
参考：[Keil Debug执行顺序](https://www.keil.com/support/man/docs/uv4cl/uv4cl_dg_debug.htm)。

### 运行中CAN离线后的恢复

再次失控的实机记录：上板role=1、board_armed=1、遥控和板间任务计数仍增长，但CAN1 ESR=0x00F80007，Bus-Off位为1。
这说明输入/任务仍在运行，CAN1已因通信错误离线。无法仅凭该快照确定接线、节点、同ID发送、终端、供电等哪一项触发错误。

双板角色在`board_link_poll()`逐毫秒服务CAN1/CAN2，原单板路径不启用该恢复。
保持现有波特率、滤波分配及AutoBusOff设置；UPPER CAN1现开启自动重发并配套10ms待发帧取消期限，CAN2及其他角色的自动重发设置保持原值。按RM0090的软件恢复要求，申请进入初始化、等待INAK、清除INRQ并等待硬件恢复。
该状态机不调用阻塞等待、不重置CAN1共享滤波块；首先申请取消三个发送邮箱，恢复过程中拒绝新帧，等所有旧请求退出邮箱且接收通知成功恢复后，才允许发送新生成的指令。
CAN启动超时导致的HAL错误状态，或已初始化但仍停在初始化模式的控制器，也由该路径完成启动及接收通知恢复。
恢复不能绕过既有遥控/板间超时、不能清除yaw故障锁定，不能自动修复持续存在的物理总线错误。
恢复后，新鲜有效的遥控/板间指令会继续控制电机；验证前应摇杆回中、发射关闭。

Watch展开`board_diag.can1`、`board_diag.can2`：

| 字段 | 含义 |
|---|---|
| `busoff_count` | 本次上电检测到的独立Bus-Off次数，不是每轮重复累加 |
| `start_retry_count` | CAN初次启动失败后开始恢复的次数 |
| `recovered_count` | 完成恢复、允许新指令进入邮箱的次数 |
| `stage` | 0正常，1等待初始化确认/取消请求，2等待总线和邮箱恢复 |
| `last_error_esr`、`last_hal_error` | 最近一次开始恢复时的硬件状态/HAL错误，恢复后保留 |
| `abort_fail_count`、`notify_fail_count` | 取消请求或恢复接收通知失败次数 |

`stage`长期非0表示恢复条件尚未满足，不能直接认定已修好；`busoff_count`持续增长也说明触发错误的原因仍在。
恢复功能加入上下板共用传输层，本次需要更新UPPER和LOWER两块板，并核对运行角色分别为1、2；协议仍为3。
参考：[ST RM0090 bxCAN Bus-Off软件恢复](https://www.st.com/resource/en/reference_manual/rm0090-stm32f407-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)。

## 本次底盘抽动修正

版本 2 在上板按 1ms 计算底盘 PID，但下板转速反馈约每 20ms 才回传一次，电流约每 10ms 才更新。
这种远程闭环改变了原控制器的时序，即使 PID 参数没改，也可能导致振荡。

版本 3 将原 `CHASSIS_TASK` 放到下板，每 1ms 直接读取 `motor_chassis_can2[]` 并发送 CAN2 四轮电流。
上板不再运行底盘 PID、不再发送四轮电流，下板板间任务也不再重复发送底盘电流。
CAN1 只传下板需要的原操作字段，约每 10ms 更新一次；期间下板仍逐毫秒处理新的本地电机反馈。
yaw电流独立按2ms转发，不需要等待底盘输入帧凑组；电机输出方向保持原值，上板yaw调试增益单独放在`control_config.h`。
上板yaw速度符号由同步方向记录核对：旧设置-1实测`last_rate_direction=2`，确认与角度变化反向，现改为`YAW_RATE_SIGN=+1`；原IMU解算和pitch速度反馈不变。

## 云台朝向与 yaw 摆动修正

实测硬件信息：枪口与底盘正前方对齐时 yaw 编码器 **3156**；
轮位为左前 ID1、右前 ID4、左后 ID2、右后 ID3，和原四轮解算顺序一致。
旧代码零位写死为6128，和实测相差约131°，会使移动方向偏转；新零位统一放在 `User/control_config.h`。
底盘相对角使用最近半圈差值，消除编码器0/8191跨界对跟随方向的影响。

期望行为：向前推右摇杆时沿枪口方向平移，原跟随开关继续决定底盘是否自动转头。
回中读数1028附近，向前推时ch1增大到1807、ch0仍在1030附近；因此前进取ch1正方向，
横移仍由ch0计算。轴选择和符号均集中在 `control_config.h`，不改遥控器解码。
当前 `CHASSIS_YAW_ECD_SIGN=+1` 保留原符号，仍需实测确认：
从上往下看逆时针旋转时，编码器增大应为+1，减小应为-1。
在方向确认前，不把“云台坐标已经实机标定正确”当作完成结论。

yaw 原代码在±180°跨界后先改写目标角，再硬钳回±180°，可能让目标差分出现一整圈跳变。
上板改用连续 yaw 测量、最近目标角表示；上电/切模式/校准恢复时同步 SMC 目标历史。
修正500ms启动等待后的任务追赶突发。用户记录：yaw曾短暂运动后触发超速保护，触发速度约-230.8°/s、误差约-5.35°；静止后约0.037°/s。
2026-11-14按实机“速度太慢”的反馈提高上板yaw响应：J=0.8、K=120、c=8（此前调试值c=4，原单板c=15），epsilon=0.8保留。
目标静止时的位置项系数从384提高为768，速度项系数从99.2变为102.4；这些是控制系数，不代表实车响应已完成验证。
原单板yaw、pitch、底盘PID参数均不因这项修改改变。
`YAW_OUTPUT_LIMIT`从±4000恢复为SMC原输出范围±16384指令单位，取消调试时额外施加的低输出上限；指令单位不是安培。
取消此前对yaw最终输出每毫秒120单位的斜率限制：从+16384降到零要约137ms，可能在控制器要求制动后仍保留旧方向输出。
保留误差0.15°、角速度1.5°/s以内的静止死区。pitch原输出限速保持不变。

上板手动yaw采用速率指令：左摇杆满杆目标进一步从90°/s提高至120°/s（`YAW_RC_MAX_RATE_DPS`），输入归一化后限在±1，不随接收机端点越界提高速度。
原摇杆方向和20通道单位死区保留；只改变解析之后的yaw控制，不改变遥控器解码、模式开关或pitch映射。
使用实际毫秒差积分目标角，同一毫秒的追赶循环不重复加角度，超过5ms的间断只补1ms，避免调试恢复后积累突转。
摇杆有效时目标允许领先当前角度30°（此前8°），防止无法运动时无限积累目标；限位修正同步移动目标差分历史，避免把参考修正算成瞬时大角速度。
从回中开始拨动时以当前角度为基准；松杆回中时只锁定一次当前角度并同步SMC历史，后续保持该参考值以产生抗扰纠偏，而不是每轮将参考跟随测量。
120°/s是满杆目标角的变化率，不是实际机械转速保证；松杆保持仍保留，尚未完成本轮实车调参。

`YAW_MOTION_GUARD_ENABLE`当前为0，按用户要求关闭此前的超速/跟踪误差锁停，不再因180°/s、45°和50ms这些调试阈值使yaw转一下就停。
改为1可重新启用原阈值锁停；锁定后仍按原模式切换/上板复位清除，遥控输入恢复不自动清除。
非有限数检查、遥控/板间断流停机和校准停机继续生效；故障隔离保持分轴处理，不让yaw异常连带关闭pitch。

## CAN1 协议版本 3

两板维持原 CAN 初始化波特率 1Mbps，标准数据帧 DLC=8，16 位数为大端。

| ID | 内容 |
|---|---|
| 0x320 | ch0(2字节)、ch1(2字节)、操作标志(2字节)、独立序号、校验 |
| 0x321 | yaw 电流(2字节)、有效标志、独立序号、版本3、0x55、0xAA、校验 |
| 0x324 | 下板 yaw 原始8字节反馈，仅用于上板状态观察，不参与底盘速度闭环 |
| 0x32F | 版本3、序号、电机在线位图、0x4C、0x4F、0x57、0、校验 |

0x320 操作标志：
bit0–1=原 key.sw，bit2=pause/小陀螺，bit3=btn_l/跟随，
bit4–9=W/S/A/D/Shift/F，bit10=原校准清零标志，bit11=原输入有效，bit12–15=版本3。
下板原底盘任务在循环入口获取完整操作快照，不依赖上板输入中断去改写运行中的 key。
校准标志只同步原本的四个底盘 PID 清零，不改变增益。

上板分别按 10ms、2ms 发送底盘输入和 yaw 电流；两种消息独立校验、独立序号、独立超时。
邮箱忙时下一毫秒重试，不等待三帧电流组。
下板底盘电流由 `CHASSIS_TASK` 唯一发送，yaw 电流由板间任务按 2ms 发送。
约每 20ms 回传 yaw 反馈和在线位图，不再转发四轮速度参与远程 PID。

校验为 0xA5 与字节0–6逐字节异或；CAN 本身还有帧 CRC。
保留必要的断流保护：原遥控/VTM 100ms 未更新时上板发禁用标志；
下板某类指令100ms未更新时对应电流置零，底盘 PID 在断流时清除历史误差，避免恢复时旧积分冲击。
yaw 原控制任务20ms未更新缓存时不继续发送旧的非零指令。
无新增中位拨杆、回中或全电机解锁条件。
