# 底盘抖动排查（2026-11-14）

用户现象：遥控方向切换时电机反复抖动、一顿一顿。当前没有实车轮速/电流时间序列，以下区分已确认代码行为与尚待验证的实车原因。未调整 PID、加速度、轮向或输出上限。

## 当前运行链路

Git 最近提交为 `63f8ab1`（2026-10-27）；双板、协议3、底盘缓变等大量功能来自当前工作区变更，不能把 HEAD 当作最新实车固件快照。

UPPER 每 10ms 通过 CAN1 0x320 传操作快照；LOWER `CHASSIS_TASK` 每 1ms 读取本地 CAN2 轮速/yaw 编码器，完成坐标变换、缓变、四轮逆解、PID，再由唯一底盘发送入口发 0x200。FreeRTOS tick=1000Hz。旧版上板远程轮速闭环已不在当前源码链路中。

检查了 `Task/chassis_task.c/h`、`User/Chassis/*`、PID、遥控解析、板间输入/超时/CAN恢复、CAN收发和初始化、任务创建与校准路径。双板工程只编入 `Task/chassis_task.c`；`User/Chassis/chassis_resolution.c`、`chassis_control_mode.c` 未编入工程，里面的重复全局量/未完成接口不是当前运行原因。

## 与反复抖动最相关的发现

### 1. 速度环输出灵敏度高，需要优先测量

底盘四轮 Kp=0.95、Ki=0.1、Kd=0，反馈是电机轴 `rpm*0.1047`，PID 输出限幅 ±10，再乘 819.2，因此最终上限是 ±8192 指令单位。比例项约为 **81.5 指令单位/rpm 误差**，仅约 100.5rpm 误差就能打满输出（不含积分）。这不是安培换算结论。

实际 PID 探针在目标0、反馈分别为 -200/+200rpm、积分历史分别清零时，输出为 +8192/-8192。证明输出容易饱和；并不证明实车反馈正好这样变化，或该增益必然不稳定。优先记录单轮目标、实际转速和电流指令，判断是否在目标附近反复正负饱和，再决定如何降低 Kp。

### 2. 输出饱和时积分仍继续累积

`User/Algorithm/alg_pid.c` 只限制积分自身，没有依据最终输出饱和方向停止积分。饱和时可积到 I=±10，与整个输出上限相同。换向时旧积分可能延迟制动，或在小误差下保留旧方向输出。

实际代码探针：目标100rad/s、反馈0持续2秒，然后目标0、反馈+5rad/s，输出仍为 **+5.2495（映射前）**，尽管此刻需要减速。示例适用于部分轮子目标过零、其他轮子仍运动等未进入全底盘零力分支的场景。它不是整车动力学仿真，也不代表正常运行每次都积满。

建议后续只在底盘速度环加入条件积分/抗饱和，再实测调参；通用 PID 同时用于发射等控制，直接全局改变算法会扩大影响。

### 3. 跟随 PID 的死区没有消除旧积分

跟随输出基于 `theta`；进入2°死区只把本轮 error 置0，历史积分仍保留。探针中30°误差持续10秒后，theta归零，仍输出约 **0.600rad/s**。如果跟随开启，可能形成对齐后仍旋转、越过零点再纠偏的现象。当前尚不知道用户抖动时跟随开关是否开启，不能把它认定为唯一原因。

建议记录 `theta`、`follow_pid.Integral_Error`、旋转目标；跟随静止区应明确积分处理，且需要核对物理反馈方向。

## 换方向迟滞与起停不连续

- LOWER 新增线加速度限制1.5m/s²、角加速度8rad/s²。实际代码在 theta=0 下，0→1m/s需667次循环，前进1m/s→横移1m/s需667次，+1→-1m/s需1334次。这会明显延缓方向切换，但本身不能解释持续高频抖动。
- 当前使用最大分量限制，不是欧氏向量模长限制；对角变化时合加速度可达约2.12m/s²，手感随方向变化。
- 遥控仍用660归一化，而实测前推1807相对中心1024偏783，实际目标为1.18636m/s；这时同轴满幅反向约需1.58秒。不能直接照搬 yaw 的归一化配置。改变端点或加速度会改变手感，需要实测后确定。
- 全底盘目标低于阈值后直接发零力并清积分，不检查实际轮速；恢复运动又重新进入闭环。它可能带来滑行/重新驱动的切换感。是否需要主动制动是控制策略选择，不能用调大输出斜率掩盖。
- 遥控轴±20死区没有连续重映射：跨阈值直接从0跳到约0.0303m/s。LOWER 缓变可减轻目标跳变，但中心噪声仍可能反复启停。

## 全向轮解算核对

设 `k=19.20320856/0.075`，`a=0.707`，`L=0.22873`：

```
w1 = k*( a*vx - a*vy - L*w)
w2 = k*( a*vx + a*vy - L*w)
w3 = k*(-a*vx + a*vy - L*w)
w4 = k*(-a*vx - a*vy - L*w)
```

轮序为左前1、左后2、右后3、右前4。theta=0 时：前进轮向 `++--`，向左 `-++-`，正旋转 `----`。这要求四轮安装及电机正转方向与矩阵一致；不能凭轮位名字证明轮向正确。若某轮打架或速度反馈符号不符，必须逐轮核对。

逆解乘减速比得到电机轴rad/s，反馈从电机轴rpm转rad/s，量纲匹配，没有发现减速比重复乘除。云台坐标旋转用的是角度制 `arm_sin_cos_f32`，与theta的度单位相符。零点3156来自项目记录；编码器增量符号仍需实测。

这是运动学逆解，未包含车体惯量、轮胎摩擦或电机扭矩模型；单靠公式不能判定动力学稳定性。当前也没有基于轮速能力的整组等比例限速，组合平移/旋转能否达到目标需实测。

## CAN、反馈与时序剩余风险

- `board_motion_enabled()` 只依据遥控/板间新鲜度，不检查每轮反馈新鲜度。轮速丢失时继续拿最后一次转速闭环；yaw编码器丢失时仍拿旧角度变换。探针确认：轮速200ms未更新，但操作快照新鲜，底盘依然使能，保留旧轮速。不要先加“全部电机上线解锁”；应先诊断每轮反馈年龄和丢帧。
- CAN2上四轮+yaw反馈、每毫秒底盘命令及每2ms yaw命令共享总线。源码是1Mbps、关闭自动重发。没有反馈实际频率/错误快照，不能判定总线已过载；发送入队成功也不等于电机收到。
- 当前有 Bus-Off 非阻塞恢复，只有现场 `board_diag.can2.busoff_count/recovered_count` 增量能证明与本次顿挫相关。不能根据历史CAN1故障直接推断本次也是总线问题。
- PID和缓变按固定1ms计算；任务延迟后 `osDelayUntil` 可能追赶，造成相同反馈重复计算。现有循环计数不能测得最大间隔或反馈年龄。需要时间戳记录才能判断现场是否发生。
- 上板VTM与遥控都会更新全局key。如果两路同时活跃且给出不同模式/轴数据，会交替覆盖；当前没有现场输入记录，不能认定发生。

## 建议的实车排查顺序

1. 先关闭底盘跟随和小陀螺，架空轮子、保持发射关闭，小输入验证四轮轮向及“命令正→反馈正”的一致性。轮向不对先修正安装映射。
2. 记录同一时间轴的 `lower_diag.ch0/ch1/mode/motion_enabled`、`chassis_motion.wheel_target_omega[4]`、`wheel_now_omega[4]`、`lower_diag.chassis_command[4]`、`chassis[i].Integral_Error`、`theta`，以及CAN2发送失败/反馈计数/Bus-Off计数增量。运动时采用记录功能，避免反复暂停造成上板断流。
3. 目标平滑但输出反复±8192，优先检查反馈符号/时序和速度环增益；反馈计数停顿或通信使能反复掉落，优先修通信。仅打开跟随后出现摆动，优先处理跟随方向和积分残留。
4. 修正底盘积分饱和处理并在小速度实测 Kp/Ki；随后再调端点、加速度、正常停车策略。当前没有足够证据给出已经验证稳定的新PID数值。
